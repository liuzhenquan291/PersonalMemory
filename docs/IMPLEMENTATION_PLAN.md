本文档把 [开发计划](DEVELOPMENT_PLAN.md) 拆成可逐项完成的实施步骤。开发必须遵守 [项目执行规则](PROJECT_RULES.md)。

## 1. 执行方式

### 1.1 状态

每个步骤只允许使用以下状态：

- `pending`：尚未开始；
- `in_progress`：正在实施，且同时只能有一个主要步骤处于此状态；
- `review`：实现完成，正在检查或代码审查；
- `blocked`：存在明确阻断条件；
- `completed`：检查和审查全部通过，且要求提交的步骤已提交；纯盘点步骤可在证据记录完成后结束。

### 1.2 单步质量门禁

每个步骤必须依次通过以下门禁：

1. **实施前检查**
   - 确认目标、非目标、依赖和验收标准；
   - 检查 Git 工作区，识别并保护用户已有修改；
   - 确认不会泄露密钥、个人数据或扩大外部访问范围；
   - 对数据库迁移、删除、历史改写等高风险操作先设计恢复路径。
2. **实现检查**
   - 运行与变更相关的格式、类型、lint、单元和集成测试；
   - 需要界面或完整链路时运行 Playwright/E2E；
   - 检查错误路径、日志脱敏、权限边界和向后兼容；
   - 运行 `git diff --check` 并检查最终 diff 中是否混入无关内容。
3. **代码审查**
   - 先进行作者自审：逐文件核对正确性、边界、失败模式和测试缺口；
   - 再进行独立审查：必须由未参与实现的 Agent、人员或独立审查上下文检查；
   - 审查结论按 `P0`（致命）、`P1`（高）、`P2`（中）、`P3`（建议）分级；
   - 存在未解决的 `P0` 或 `P1` 时禁止提交；`P2` 必须修复，或由用户/项目负责人明确接受并记录理由；
   - 修复审查问题后重跑受影响测试，并复核修改。
4. **提交与收尾**
   - 只暂存本步骤相关文件；
   - 按 `<type>: <description>` 创建原子提交；
   - 提交后确认工作区状态和提交内容；
   - 在任务报告或 CI/审查记录中更新步骤状态、提交 SHA、验证证据、已知限制和下一步依赖；不要为在同一提交中记录该提交自身 SHA 而执行 amend 或制造额外提交；
   - 默认不推送远端。

### 1.3 最低检查矩阵

| 变更类型 | 必须检查 | 需要时增加 |
|---|---|---|
| 文档 | 链接、事实、冲突、`git diff --check`、读者可理解性 | 独立读者测试 |
| TypeScript | format、typecheck、lint、相关 Vitest | build、集成测试 |
| API | schema、成功/错误用例、兼容性、鉴权和日志 | 契约测试、负载测试 |
| 数据库 | migration up、数据校验、重复执行 | rollback/restore、旧版本升级 |
| Web UI | typecheck、组件测试、键盘操作、空/错/加载态 | Playwright、视觉检查、可访问性 |
| MCP/适配器 | 协议校验、超时、错误映射、上下文预算 | 至少一个真实客户端验收 |
| 安装/升级 | 干净环境、重复安装、失败提示、数据保留 | 多平台、多架构、升级回滚 |
| 删除/隐私 | 删除清单、日志脱敏、残留扫描 | 备份恢复后复测、威胁建模 |

### 1.4 统一验证入口与例外规则

- M1.1 完成后，仓库根必须提供统一 `verify` 命令，至少串联 format check、typecheck、lint、unit test 和 build；此前使用上游原生命令，并在基线报告中逐项记录。
- 集成测试、E2E、安全、迁移和性能检查使用独立脚本，但必须可从仓库文档发现，并返回可靠退出码。
- CI 中 format、typecheck、lint、unit test、build 和受影响的契约/迁移测试为 required checks。
- 不允许为了通过门禁而静默跳过测试。环境确实不具备时，记录原因、影响范围、复现条件和补测负责人，并由用户明确接受。
- Flaky 测试必须进入隔离清单，记录 issue、重试证据和修复期限；不得无限重试后宣称通过。

## 3. M0：上游基线与可重复运行

### M0.0 冻结 Git 迁移 Runbook

目标：让不了解聊天背景的开发者也能以唯一、可恢复且不改写共享历史的方式引入上游。

固定拓扑与方案：

```text
origin   = git@github.com:liuzhenquan291/PersonalMemory.git
upstream = git@github.com:TencentCloud/TencentDB-Agent-Memory.git

origin/main: 现有 PersonalMemory 初始提交与文档提交
upstream v1.0.1: 505877cc5160d3ea5cdb5bbd72902db03c97dd10

迁移策略：从当前 main 创建 integration/upstream-v1.0.1，
在该分支使用 --no-commit --no-ff --allow-unrelated-histories 合并 v1.0.1，
通过正常 merge commit 同时保留两条历史；验证通过后 main 仅做 fast-forward。
不使用 rebase、orphan、subtree、历史重写或 force push。
```

执行边界：

- 先创建本地备份分支 `backup/pre-upstream-v1.0.1` 指向迁移前 `main`；记录迁移前 `main`、`origin/main` 和上游 tag 三个 SHA；
- M0.1 只创建备份分支和 `integration/upstream-v1.0.1`，不获取或合并上游；
- M0.2 在独立临时 worktree 验证未经修改的上游基线，不修改集成分支；
- M0.3 才在集成分支添加/获取 `upstream`、验证 tag SHA，并使用 `--no-commit --no-ff --allow-unrelated-histories` 合并已校验 SHA；
- 合并暂停态逐文件处理冲突，README 保留 PersonalMemory 定位并保留上游归属，LICENSE 不删除；检查和独立审查通过后才能创建 merge commit；若意外产生自动提交，立即停止；
- 整个 M0 退出门通过前不移动 `main`；通过后，`main` 只能 fast-forward 到集成分支；
- 不自动 push。首次推送这种双历史合并结果前必须向用户展示提交图和 diff 摘要并取得明确授权；
- 若任何 SHA、分支状态或冲突范围与 Runbook 不符，立即停止，不自行选择替代 Git 策略。

恢复方法：集成验证失败时切回 `main`，保留失败分支供审查，不需要 reset。若 `main` 已 fast-forward，切换到备份分支仍可恢复旧状态；是否移动 `main` 回退必须由用户决定。

检查：使用 `git merge-base --is-ancestor` 分别验证迁移结果包含旧 `main` 和上游 v1.0.1；工作区无未跟踪密钥；提交图与上述拓扑一致。

审查重点：备份 ref 是否准确；是否存在历史改写或 force push；冲突处理是否丢失上游许可证或 PersonalMemory 文档。

建议提交：`docs: 固化上游基线迁移方案`。Runbook 完成并审查通过后才能开始 M0.1。

### M0.1 建立安全迁移点

目标：在引入上游前确保当前 PersonalMemory 文档和历史可恢复。

实施：

- 记录当前 `main`、`origin/main` 和文档提交 SHA；
- 创建明确的迁移分支或标签；
- 确认工作区干净；
- 严格按 M0.0 Runbook 创建备份分支和集成分支，不添加/fetch/merge 上游，也不临时改变迁移策略。

检查：引用均可解析，恢复演练不依赖未提交文件，不改写远端历史。

审查重点：是否可能丢失当前文档提交；是否误把三条上游代码线当作可直接合并的普通分支。

建议提交：该步骤可无代码提交，但必须在任务报告记录 refs、SHA、检查和独立审查结论。

### M0.2 验证未经修改的上游 v1.0.1

目标：在合并前记录精确上游 SHA 的原始构建、测试和供应链基线，避免把集成冲突误归因给上游。

实施：

- 在独立临时 clone/worktree 精确检出 `505877cc5160d3ea5cdb5bbd72902db03c97dd10`；
- 校验 tag 和提交签名/来源信息；
- 固定 Node.js 和包管理器版本并执行上游原生 build、typecheck、Vitest 及可运行的集成测试；
- 记录通过、失败、跳过、环境限制、支持矩阵和构建耗时；standalone 冷启动、基础搜索和资源占用在 M0.4 黄金链路中实测；
- 不修改上游文件，不为追求全绿而静默跳过或修复测试；
- 扫描当前 tree 和将要引入的 tree 是否包含密钥；审查 lockfile、安装/生命周期脚本、许可证和新增二进制文件；生成初始依赖与 SBOM/许可证基线。

检查：临时 worktree 的 `HEAD` 等于指定 SHA 且保持干净；基线失败有原始证据和分类；秘密、许可证、供应链、支持矩阵和性能基线有记录。

审查重点：测试是否真实执行；是否混入分支头或 v2 文件；安装脚本是否有高风险行为；是否使用真实个人数据或生产密钥。

建议提交：`docs: 记录未经修改的 v1.0.1 基线验证结果`。

### M0.3 合并上游并执行集成回归

目标：通过正常 merge commit 同时保留 PersonalMemory 与上游历史，并证明冲突处理没有破坏基线。

实施：

- 在集成分支添加/获取 `upstream` 并再次校验 tag SHA；
- 使用 Runbook 指定的 `--no-commit --no-ff --allow-unrelated-histories` 合并精确 SHA；
- 现有文档通过第一父历史原样保留，只解决实际路径冲突；禁止额外 cherry-pick、rebase 或历史改写；
- 根据 M0.2 已确认的 P1，在合并暂停态移除工作树中的疑似硬编码凭据、生成锁文件并修复或裁剪 high/critical 依赖；这些安全基线调整必须逐项记录，不得夹带其他产品功能；
- 在合并暂停态增加至少一组能被根项目 `npm test` 发现的核心 smoke 测试；
- 在合并暂停态运行 diff、构建、类型、测试、许可证和秘密检查，并完成独立审查；
- 通过后创建 merge commit，再运行一次完整集成回归；
- 记录相对 M0.2 原始基线新增的失败或行为变化。
- 记录 Node、包管理器、Docker、操作系统、CPU 架构、磁盘空间和构建耗时支持矩阵；
- standalone 冷启动、基础搜索延迟、SQLite/sqlite-vec 与资源占用统一在 M0.4 黄金链路中校准。

创建 merge commit 的最低门禁：根项目 build 通过；TypeScript SDK build 与 32 项测试通过；Python SDK 34 项测试通过；根项目至少一组核心 smoke 测试可被 `npm test` 发现并通过；秘密扫描无非占位凭据；根项目和 TypeScript SDK 的 npm audit 均无未接受的 high/critical。

检查：merge commit 同时以旧 PersonalMemory 和上游提交为祖先；文档未丢失；无 v2 团队文件；集成结果相对原始基线的差异有解释。

审查重点：冲突解决是否改动上游业务代码；Git 历史是否可持续同步；新增失败是否被掩盖。

建议提交：`chore: 建立 TencentDB Agent Memory v1.0.1 基线`。疑似凭据移除、锁文件、阻断级依赖修复和最小 smoke 测试属于本次安全基线，随 merge commit 一并落地；非阻断修复在 merge 后单独使用 `fix`。

### M0.4 跑通 standalone Gateway 黄金链路

目标：验证独立 Gateway 能完成最小记忆闭环。

边界：本步骤只增加隔离的基线验证脚本，不开发 PersonalMemory 产品功能。四个产品 ADR 必须在 M0.5 完成，并在进入 M1 前通过 M0 退出门。

实施：

- 执行健康检查；
- 写入固定测试会话；
- 等待或触发 L1 提炼；
- 查询 L0、搜索 L1，并验证来源；
- 清理测试实例，不触碰真实记忆目录。

检查：同一脚本可重复运行；成功和超时路径都有明确结果；数据目录隔离。

审查重点：异步等待是否稳定；测试是否依赖偶然时间；失败时是否泄露正文或密钥。

建议提交：`test: 增加 standalone 记忆黄金链路`。

### M0.5 架构清单、威胁模型与 ADR

目标：基于实际代码而非 README 假设冻结 Phase 1 边界。

审查重点：是否把源码推断写成已验证事实；删除和备份边界是否遗漏。

建议提交：`docs: 完成基线架构、威胁模型与关键 ADR`。

### M0.6 建立上游同步 Runbook

检查：演练能区分修复、功能、架构漂移和高风险依赖；不同步的提交有理由；不实际合入未经确认代码。

审查重点：Runbook 是否假定三条上游历史可互相合并；是否遗漏安装脚本和数据格式变化。

## 4. M1：PersonalMemory 工程骨架

### M1.1 建立 workspace 和目录边界

目标：在不重写上游核心的前提下建立可扩展工程结构。

实施：建立 `apps/web`、`apps/gateway`、`packages/personal-memory`、`packages/mcp-server` 和共享配置；上游核心保持可辨识边界；同时建立 schema version、migration runner、事务边界、幂等迁移规范和旧版本 fixture。每次 schema 变更必须随功能提交迁移与测试，不能等到发布阶段补做。

检查：统一 install/build/typecheck/test/verify 可执行；依赖方向无循环；上游测试仍通过；空库初始化、重复迁移、失败回滚或备份恢复测试通过。

审查重点：是否过早搬移上游文件；包边界是否真正减少未来同步冲突。

建议提交：`chore: 建立 PersonalMemory workspace`。

### M1.2 配置、数据目录和密钥边界

目标：建立单一配置入口与安全默认值。

实施：定义配置 schema、默认本地数据目录、环境变量覆盖、模型 provider 和密钥加载规则。

安全默认值：Gateway/Web 默认只监听 loopback；非 loopback 必须显式配置并启用认证；数据目录采用用户私有权限并防止符号链接越界；默认禁止遥测和模型/embedding 外联，启用外联前展示 provider、目标地址和发送字段。

检查：无密钥可安全启动到配置引导；错误配置得到可操作提示；密钥不写日志或仓库；网络隔离环境证明默认零外联；代理环境变量不会绕过 provider allowlist。

审查重点：默认是否外发数据；路径是否可能覆盖用户文件；配置优先级是否明确。

建议提交：`feat: 建立个人版配置与数据目录`。

### M1.3 PersonalMemory Gateway 外观层

目标：在上游 v1.0.1 `feat/server` API 外侧增加稳定的个人版边界，不侵入核心。

实施：建立 Hono 服务、健康/版本端点、错误模型、请求 ID 和上游客户端封装；定义 Web↔Gateway 信任模型、认证/会话、严格 CORS、CSRF 防护、请求体大小、超时和基础速率限制。

检查：API 契约测试、错误路径、超时、关闭流程、日志脱敏全部通过；验证默认 loopback、非 loopback 无认证拒绝启动、CORS/CSRF、目录穿越、符号链接、超大请求和限流。

审查重点：是否复制上游业务逻辑；错误是否泄露路径、密钥或记忆正文。

建议提交：`feat: 建立 PersonalMemory Gateway`。

### M1.4 Web 应用壳

目标：提供可访问的个人记忆管理入口。

实施：React/Vite、路由、查询客户端、基础布局、错误边界、空状态和设置入口。

检查：build、typecheck、组件测试、键盘导航和 Playwright 启动测试。

审查重点：是否把团队概念带入个人 UI；错误/加载/空状态是否完整。

建议提交：`feat: 建立个人记忆 Web 应用`。

### M1.5 开发环境联合启动

目标：一条开发命令启动 Gateway 与 Web，并显示健康状态。

检查：首次和重复启动、端口占用、进程退出、临时数据隔离；macOS 与 Linux 至少记录一种实测和另一种待测状态。

审查重点：子进程泄漏、硬编码路径、错误退出码和隐式下载安装。

建议提交：`chore: 增加本地联合开发命令`。

M1 退出门：新成员通过仓库文档可在 15 分钟内启动开发环境；上游核心测试未回退。

## 5. M2：个人记忆最小闭环

### M2.1 固化测试数据和验收场景

建立不含真实个人信息的版本化黄金数据集，最终不少于 100 个带期望答案的样本，覆盖偏好、事实、决定、冲突、过期和无答案场景。

检查：数据确定性、可重置、可公开；期望结果和评测版本明确；小型 smoke 子集可在每次提交运行，完整 100 样本评测可在里程碑门运行。

审查重点：评测是否只覆盖成功路径；是否存在答案泄漏。

建议提交：`test: 建立个人记忆黄金数据集`。

### M2.2 会话捕获与导入

实现单会话写入、批量导入、幂等键、进度和失败重试。

检查：重复导入、部分失败、超大输入、非法角色、敏感日志和取消操作；默认零外联测试通过，启用 provider 时发送前字段清单与用户提示可验证。

审查重点：是否重复生成记忆；失败是否留下不可恢复的半状态。

建议提交：`feat: 实现会话捕获与导入`。

### M2.3 统一查询与预算召回

封装 L0/L1 搜索及 L2/L3 读取，加入条数、字符和超时预算。

检查：关键词、语义、混合、无结果、超时降级；在版本化数据集记录 Recall@K、错误注入率、过期记忆命中率、无答案拒答率、字符/token 预算和 P95 延迟。

审查重点：过滤条件是否在召回前生效；预算是否可绕过；排序是否稳定。

建议提交：`feat: 实现预算受控的记忆召回`。

### M2.4 记忆列表、搜索和详情

实现列表、筛选、分页、详情和 L3→L2→L1→L0 来源下钻。

检查：空/错/加载态、分页边界、长文本、键盘操作、移动窄屏和 Playwright 主路径。

审查重点：UI 是否误导用户把推断当原文；来源链是否真实可达。

建议提交：`feat: 增加记忆浏览与来源追溯`。

### M2.5 修改、失效和受控删除

实现 L1 修改/删除、L2/L3 写入以及 PersonalMemory 状态层；M2 只承诺明确标注的软删除/局部删除，完整级联删除在 M3.4 交付，界面不得提前宣称“彻底删除”。

检查：并发修改、重复删除、删除预览、失败恢复、检索残留和日志残留。

审查重点：删除范围是否准确展示；tombstone 是否阻止恢复或重新索引时数据复活；上层资产如何处理来源已删除状态。

建议提交：`feat: 实现记忆纠错与删除`。

### M2.6 导出、备份和恢复

实现可读 Markdown/JSON 导出、完整备份清单、校验和和恢复验证。

检查：空库、大数据、损坏包、版本不兼容、恢复后搜索一致性。

审查重点：导出是否遗漏来源或状态；备份是否包含明文密钥。

建议提交：`feat: 实现记忆导出与恢复`。

M2 退出门：黄金链路“导入→提炼→搜索→追溯→纠错→导出→受控删除”通过自动化 E2E；100 样本评测报告和上下文预算检查完成，但不得把受控删除宣传为彻底删除。

## 6. M3：可信记忆治理

### M3.1 记忆收件箱

实现 `pending/approved/rejected` 状态和接受、修改后接受、拒绝操作。

检查：状态迁移、批量操作、重复提交、失败恢复；未批准高影响记忆默认不自动注入。

审查重点：审核状态是否与上游记忆内容解耦；是否存在绕过审核的召回路径。

建议提交：`feat: 增加记忆审核收件箱`。

### M3.2 冲突、合并和替代关系

实现相似候选、人工合并、`supersedes`、有效期和冲突展示。

检查：互相矛盾、循环替代、历史时间线、合并撤销。

审查重点：自动化是否越权替用户做事实判断；旧记忆是否仍被错误召回。

建议提交：`feat: 增加记忆冲突与替代治理`。

### M3.3 来源时间线和审计

记录生成、审核、修改、召回、导出和删除事件，但不记录敏感正文。

检查：审计完整性、时间顺序、脱敏、保留期和批量查询性能。

审查重点：审计数据本身是否形成新的隐私泄露面。

建议提交：`feat: 增加记忆时间线与审计`。

### M3.4 级联删除与隐私控制

建立来源、派生资产、FTS/向量索引、缓存、临时文件、导出物和备份的删除矩阵及用户确认流程；ADR 明确备份采用重写、密钥销毁还是保留期到期策略。

检查：删除后全局残留扫描、重启/重新索引后复测、备份恢复后复测、tombstone 防复活、取消和部分失败。

审查重点：不可恢复操作的确认强度；备份保留政策是否清晰。

建议提交：`feat: 实现可验证的级联删除`。

M3 退出门：错误记忆可被识别、纠正和完整删除，所有高影响操作可追溯。

## 7. M4：跨 Agent 接入

### M4.1 冻结 MCP 工具契约

定义最小工具集：搜索、读取、捕获、反馈和遗忘；采用版本化 schema。

检查：协议校验、错误码、超时、分页、上下文预算和敏感字段；加入不可信记忆内容/提示注入隔离以及删除确认不可绕过的测试。

审查重点：工具粒度是否导致整库暴露；模型是否可以绕过用户确认删除数据。

建议提交：`feat: 定义 PersonalMemory MCP 契约`。

### M4.2 实现 MCP Server

复用 Gateway，不复制记忆业务逻辑；增加 stdio/必要传输、生命周期和诊断。

检查：协议测试、异常断连、并发请求、关闭流程和日志脱敏。

审查重点：进程权限、路径暴露、任意文件读取和提示注入边界。

建议提交：`feat: 实现 PersonalMemory MCP Server`。

### M4.3 首个真实客户端验收

按 ADR 选择首个客户端，完成安装、捕获、召回和反馈闭环。

检查：全新配置、已有配置保护、卸载恢复、真实会话 E2E。

审查重点：安装器是否覆盖用户配置；注入内容是否超过预算。

建议提交：`feat: 接入首个 MCP 客户端`。

### M4.4 第二客户端可移植性验证

不修改核心语义接入第二客户端，验证协议独立性。

检查：相同测试问题得到等价的权限范围和召回结果。

审查重点：是否通过客户端特例污染核心；行为差异是否有文档。

建议提交：`feat: 验证跨 Agent 记忆接入`。

M4 退出门：两个 Agent 能安全共享同一记忆库，并保持一致治理和预算规则。

## 8. M5：安装、升级与发布

### M5.1 一条命令安装器

实现环境检查、组件获取、配置引导、初始化、启动和健康检查。

检查：干净环境、重复安装、断网、端口占用、缺少 Docker/Node、无密钥、错误密钥和中断恢复。

审查重点：远程脚本执行风险、下载校验、提权范围、默认数据外发和失败残留。

建议提交：`feat: 增加一条命令安装流程`。

### M5.2 升级和数据库迁移

基于 M1.1 已建立的 migration runner，实现面向用户的版本检测、升级编排、升级前备份、迁移、健康验证和失败回滚；此步骤不得首次引入 schema 版本化能力。

检查：至少覆盖前一版本升级、重复迁移、迁移中断、旧数据恢复。

审查重点：schema 兼容、不可逆步骤和磁盘空间不足。

建议提交：`feat: 实现安全升级与迁移`。

### M5.3 备份、恢复和卸载

提供明确命令；卸载默认保留数据，清除数据必须二次确认并列出目标路径。

检查：备份校验、跨安装恢复、卸载后进程/端口/配置状态、保留数据可再次使用。

审查重点：路径解析、递归删除目标、符号链接和误删风险。

建议提交：`feat: 完善备份恢复与安全卸载`。

### M5.4 发布候选验证

执行全量测试、许可证扫描、依赖与密钥扫描、性能基线、故障注入、长时间运行和安装矩阵。

检查：所有发布阻断项关闭；已知限制、支持平台和数据处理说明完整。

审查重点：发布包内容、第三方归属、默认安全配置和可回滚性。

建议提交：`chore: 准备首个发布候选版本`。

M5 退出门：支持的平台一条命令安装成功，从空机到首条召回不超过 15 分钟，升级可回滚，备份可恢复。

## 10. 开发停止条件

出现以下任一情况时，停止进入下一步骤并先处理问题：

- 基线、数据模型或删除语义与计划假设不一致；
- 测试无法稳定复现或需要真实个人数据才能通过；
- 发现可能泄露密钥、记忆正文或开放未鉴权网络端口；
- 数据迁移或删除没有可验证的恢复方案；
- 上游同步需要大面积修改核心，超出“少改核心”的规则；
- 存在未解决的 P0/P1 审查问题；
- 用户新决定与现行项目规则冲突但尚未完成规则更新。
