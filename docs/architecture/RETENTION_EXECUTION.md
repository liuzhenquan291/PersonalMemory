# L0/L1 保留期执行契约

状态：frozen

适用步骤：M4.6.6.1

后续实现：M4.6.6.2

## 1. 目标

把 M4.6.5 已落账的独立 L0/L1 保留天数接入可验证的自动清理，同时保持以下不变量：

- 未明确授权执行前不删除任何数据；
- L1 复用 M3.4 的适用删除矩阵；来源 L0 和可读 L0 只按独立 L0 截止点处理；
- 任何受管副本无法安全删除时，不删除仍可作为重试事实源的索引或来源元数据；L1 tombstone 可先阻止召回，但不能被误写成仍 active；
- 有效保留期执行授权下恢复旧备份后，过期记录在产品 Gateway、Hook 和 Web 可用前再次清理；未授权或已撤销时不提供该保证并明确显示 disabled；
- 日志、状态和审计只记录 revision、计数、阶段和错误码，不记录正文、原始 ID 或路径。

## 2. 授权边界

M4.6.5 的 `l0_retention_days` / `l1_retention_days` 只是策略配置，不构成物理删除授权。M4.6.6.2 必须新增独立、版本化的保留期执行授权，默认关闭，并固定披露：

1. L1 到期会永久删除或重写该 L1、FTS/向量索引、精确派生内容和可读 L1；来源 L0 与可读 L0 只有独立越过 L0 截止点时才删除，显式 M3.4 彻底删除仍会删除全部已知来源；
2. 任何仍登记为 active 的可读导出和完整备份会整件删除，不做选择性改写；
3. 用户自行复制、移动、同步或改名的副本无法发现，不在完成声明内；
4. 清理按本机自然日计算，天数或披露版本变化后必须重新授权；
5. 关闭执行只阻止新一轮清理，不恢复已删除数据。

授权必须绑定 retention disclosure version、当前 policy revision、L0/L1 天数和登记副本处理方式。任一绑定项变化立即失效；逐请求确认不能替代持久授权。

## 3. 到期与批次

- L0 使用 `recorded_at`，L1 使用 `updated_time`；空值、非法时间和未来时间均 fail closed 保留，并计入脱敏异常计数。
- 截止点沿用既有本机自然日语义：保留今天及向前 `days - 1` 个自然日，删除严格早于起始点的记录。
- L0/L1 分别计算截止点；任一保留期为 `null` 时该层不清理。
- 每轮最多规划 100 条 L0 和 25 条 L1；超过部分留给后续轮次，不在单次维护中无界扫描或删除。运行状态区分 `disabled`、`not_applicable`、`draining`、`drained` 和 `partial`，不能用一个 success 布尔值混淆批次成功与候选清零。
- 同一轮先冻结候选摘要和 policy/authorization revision；执行前 revision 变化则整轮放弃。
- `drained` 必须由同一冻结 policy/authorization revision 和截止点下的全范围复查证明 `remaining_eligible=0`；单批成功只能是 `draining`。revision 或截止点变化立即使旧证明失效并重新规划。

## 4. 删除顺序

### 4.1 L1

每条到期 L1 复用 M3.4 服务端级联删除能力，但采用 retention 专用变体以保持 L0/L1 天数独立：

1. 写入无正文 tombstone；
2. 精确替换 L2/L3 派生正文；
3. 原子重写可读 L1；
4. 保留真实 `source_message_ids` 指向且尚未越过 L0 截止点的 L0 及可读 L0；只有同时满足 L0 到期条件的来源才进入本轮独立 L0 删除集合；
5. 删除登记导出和备份整件副本；
6. 清理审核、有效期和关系元数据；
7. 前序全部成功后删除 L1 SQLite/FTS/向量索引；
8. 重查 L1、派生、可读 L1、登记副本和产品元数据；L0 只按独立截止点验证，残留非零即 partial。

自动执行使用保留期授权代替逐条 `ERASE L1:<id>` 交互，但不能绕过适用的删除步骤、验证和失败顺序。显式彻底删除继续使用 M3.4 全级联并删除全部已知来源 L0；retention 专用变体不得改变该语义。

L1 tombstone 成功后的持久重试事实源是 tombstone、尚未删除的 L1 索引行及其 `source_message_ids` 元数据；产品召回受 tombstone 抑制。只有派生、可读副本、登记副本和产品元数据全部完成后才删最后的 L1 索引定位。进程重启后从 tombstone 与仍保留的 L1 行重新规划，不得临时恢复 active 状态。

### 4.2 独立 L0

未被 L1 级联覆盖的到期 L0 按以下顺序处理：

1. 原子重写可读 L0 副本；
2. 删除所有仍登记为 active 的导出和备份，并更新登记账本；
3. 通过上游存储接口删除 L0 元数据、FTS 和向量索引；
4. 重查可读副本、登记路径和上游 L0，残留非零即 partial。

受管副本或可读副本清理失败时必须保留活动 L0，不能先删索引后丢失重试事实源。

## 5. 调度、并发和失败

- 受管 Hook worker 每分钟只触发一次轻量 maintenance 请求；Gateway 账本保证同一自然日最多一个活动清理 lease，并允许失败批次在退避后重试。
- lease、policy revision、authorization revision、截止点、候选摘要、阶段计数、状态和错误码持久化；不保存候选 ID、正文或路径。
- Gateway 进程重启后可从活动数据重新规划；同一条删除必须幂等。
- 锁竞争、上游不可用、账本异常或验证失败均返回 degraded/partial，不影响 Agent 当前响应，但 doctor 必须显示脱敏告警。
- 清理不得与备份、恢复、升级或彻底删除并行；无法取得数据生命周期互斥锁时跳过本轮。

## 6. 备份与恢复防复活

- 创建完整备份前必须取得明确 preflight 状态：没有配置保留期或执行授权从未启用时返回 `not_applicable`/`disabled`，允许沿用 M5.3 备份但不得声称满足保留期；有效执行授权下必须持续运行有界批次，直到同一冻结 revision/截止点下复查 `remaining_eligible=0` 并得到 `drained`，`draining`、`partial` 或 revision 变化均使备份 fail closed。
- 恢复完成后先保留所有受管服务停止，运行 schema 迁移并重放当前安装状态目录中独立保存的保留期授权封套。
- 私有状态目录中的封套必须包含授权所绑定的策略快照和单向摘要，不含正文、候选 ID 或副本路径；恢复出的旧策略或旧授权不能覆盖当前安装的策略与执行授权。恢复前当前授权有效时，无法把同一封套安全应用到 staging、安装身份或披露不一致、清理不为 `drained` 均直接中止恢复并回滚原数据，不允许启动恢复数据或把问题推迟到服务启动后重新授权。
- 恢复前还必须从当前活动数据取得已登记副本目录的完整快照，放入仅本次恢复使用的私有临时状态；恢复 staging 合并该目录后才能判断旧备份之外的新导出/备份，避免旧 `personalmemory.sqlite` 回滚登记账本。
- 若当前授权有效，必须在离线恢复 staging 中完成到期清理和残留验证，再切换数据目录；作为恢复输入的登记备份应在 staging 验证和数据切换成功后、服务启动前删除并更新目录。任何清理、切换或登记副本删除失败都使恢复失败，原数据回滚且服务按原数据重启。
- 若当前安装从未授权或已明确撤销执行保留期，显式恢复仍可按 M5.3 原语义进行，但状态必须明确显示 retention execution disabled，不能宣称恢复后已满足保留期。用户若要求恢复同时沿用有效保留承诺，必须先在原数据上建立可应用于 staging 的有效封套，否则取消恢复。
- M4.6.6.2 未完成上述离线恢复门禁前，不得宣称“备份恢复后不复活”，也不得启用生产自动清理。

## 7. 用户可见状态

认证 API 和 doctor 至少显示：执行授权状态、绑定的 policy revision、最近开始/完成时间、最近状态、L0/L1 计划/删除/残留计数、登记副本删除计数和固定错误码。不得返回候选 ID、正文、工作目录或副本路径。

## 8. 非目标

- 不自动发现未登记的外部副本；
- 不选择性改写完整备份；
- 不改变显式彻底删除的 Web 强确认；
- 不清理 L2/L3 中无法精确归因的语义改写；
- 不在本步骤增加团队、远程存储或逐对象加密。
