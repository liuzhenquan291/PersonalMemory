# PersonalMemory 开发计划

> 状态：Draft v0.1  
> 日期：2026-08-06

本计划的设计与实施受 [项目执行规则](PROJECT_RULES.md) 约束；二者冲突时，应先明确更新执行规则，再调整计划。

## 1. 产品目标

为单个用户提供一个可在本机运行的 AI 长期记忆中心，让多个 Agent 能安全地沉淀、检索、审阅和迁移个人记忆，同时避免把全部历史对话无差别塞入上下文。

首个可用版本只验证一个闭环：

`会话导入/捕获 → 分层提炼 → 检索召回 → 人工审阅纠错 → 导出/删除`

### 1.1 目标用户

- 同时使用 Codex、Claude Code、CodeBuddy 等多个 Agent 的个人开发者；
- 希望跨会话保留项目决定、偏好与工作流程的知识工作者；
- 对本地存储、隐私和可控性有明确要求的用户。

### 1.2 MVP 不做

- 多组织、多团队协作和复杂 RBAC；
- 公共技能市场；
- 企业计费、SLA 与大规模集群部署；
- 全自动、不可审阅的记忆写入；
- 同时重写上游四类资产的所有实现。

## 2. 名称结论

### 2.1 是否合适

结论：**适合作为工程名和 MVP 名，不建议直接锁定为最终商业品牌。**

优点：语义准确、学习成本低，与上游团队级 Memory Hub 有清晰区分。

缺点：过于通用，搜索和品牌辨识度弱；可能让用户误以为是笔记产品、系统内存工具或单纯聊天记录库。

### 2.2 命名策略

- 近期：仓库和内部版本继续使用 `PersonalMemory`。
- 发布前：完成商标、域名、GitHub/npm/PyPI 和应用商店重名检查。
- 若产品化：采用独特主品牌，副标题使用 “Personal AI Memory” 或“个人 AI 记忆工作台”。
- 明确标注“基于 TencentDB-Agent-Memory”，但不使用易造成官方背书误解的名称或视觉资产。

## 3. 架构基线

### 3.1 继承的上游能力

以 TencentDB-Agent-Memory 当前架构为基线：

- Chat Memory：L0 Conversation → L1 Atom → L2 Scenario → L3 Core/Persona；
- Skill：从成功会话和工具轨迹提炼可复用流程；
- Wiki：将个人文档组织成可搜索、可关联的知识页；
- CodeGraph：索引文件、符号、调用关系和影响范围；
- Memory Core：资产处理、检索和 API；
- Memory Panel：资产查看与治理；
- Proxy/SDK：连接不同 Agent 框架。

检索采用分层召回：L2/L3 用于快速恢复上下文，细节通过 BM25、向量召回和融合排序下钻到 L1/L0，并受条目数、字符预算和超时约束。

### 3.2 PersonalMemory 的差异化层

1. **个人空间**：删除团队和组织概念对核心路径的干扰，默认只有一个本地 Owner。
2. **记忆收件箱**：新提炼的高影响记忆先进入待审阅状态；用户可接受、修改、拒绝或合并。
3. **来源与时间线**：每条记忆展示来源会话、提炼链路、更新时间、置信度和失效状态。
4. **隐私控制**：敏感字段识别、来源级采集开关、外部模型调用提示、数据保留期和彻底删除。
5. **跨 Agent 连接**：通过稳定的本地 API/MCP 或适配器向 Codex、Claude Code、CodeBuddy 提供一致召回。
6. **便携性**：一键导出可读 Markdown/JSON 与完整备份；数据库索引可重建，不作为唯一事实源。

### 3.3 建议的运行边界

```text
Agent adapters / MCP / Proxy
            │
            ▼
PersonalMemory Gateway
  ├─ capture/import
  ├─ recall/search
  ├─ review/governance
  └─ export/delete
            │
            ▼
Memory pipeline
  ├─ Chat: L0 → L1 → L2 → L3
  ├─ Skill extraction
  ├─ Wiki ingest
  └─ CodeGraph indexing
            │
            ▼
Local storage
  ├─ SQLite: metadata, FTS, jobs, audit
  ├─ Vector index: semantic retrieval
  └─ Files: raw evidence and portable assets
```

原则上沿用上游服务边界，不在第一阶段拆成更多微服务。个人部署优先单机容器组合，后续再评估桌面应用封装。

## 4. 开发路线

### Phase 0：产品与上游基线（1 周）

工作：

- 记录上游 fork 的准确提交 SHA、版本、许可证和依赖清单；
- 跑通上游完整部署、测试与最小会话召回；
- 建立 `upstream` remote、同步规范和差异补丁原则；
- 写 5 个端到端验收场景及一份隐私威胁模型；
- 决定 MVP 首发适配器，建议只选 Codex/通用 MCP 其中一个。

退出标准：干净环境可重复启动；基线测试结果有记录；上游代码尚未被大面积改名或重构。

### Phase 1：个人版最小闭环（2 周）

工作：

- 单用户本地配置和首次启动引导；
- 会话导入/捕获与 L0–L3 管线；
- 统一搜索和预算受控的召回接口；
- 最小管理页：列表、搜索、详情、来源追溯；
- 记忆修改、软删除和彻底删除；
- JSON/Markdown 导出与恢复验证。

退出标准：用户可以完成“导入一段会话—产生记忆—下一会话正确召回—纠错—导出—删除”的全流程。

### Phase 2：可信记忆治理（2 周）

工作：

- 记忆收件箱和 approve/reject/edit/merge 工作流；
- 冲突检测、`supersedes` 关系、有效期和过期提示；
- 敏感信息规则与来源级采集开关；
- 原始证据、派生资产和索引的级联删除；
- 处理任务状态、失败重试、审计记录与可观测性。

退出标准：错误记忆不会静默覆盖有效记忆；任何记忆可追溯、可纠正、可完整删除。

### Phase 3：跨 Agent 与知识资产（2–3 周）

工作：

- 完成首发 Agent 适配器并冻结版本化 API；
- 加入第二个 Agent 适配器验证可移植性；
- 在真实需求验证后，逐项开放 Skill、Wiki、CodeGraph；
- 支持按项目、来源和记忆类型配置 Agent 装配；
- 加入增量同步和失败隔离。

退出标准：同一记忆库能在两个 Agent 中得到权限一致、预算一致且可解释的召回结果。

### Phase 4：发布准备（1–2 周）

工作：

- 安装、升级、备份恢复和卸载流程；
- 提供面向普通用户的一条命令安装入口，覆盖环境检查、初始化、启动和健康检查；
- macOS/Linux 兼容性与数据迁移测试；
- 第三方许可、隐私说明、安全默认值和日志脱敏审查；
- 基准测试、故障注入和长时间运行测试；
- 名称、域名、商标和发布渠道检查。

退出标准：支持的平台可通过一条命令完成安装和启动；从空机安装到首条召回不超过 15 分钟；重复安装不破坏已有数据；升级失败可回滚；备份可恢复；发布包不包含密钥或个人数据。

## 5. 优先级 Backlog

### P0

- 上游基线与可重复部署；
- 会话捕获、L0–L3 处理、召回；
- 来源追溯与人工纠错；
- 导出、备份、彻底删除；
- 一个 Agent 适配器；
- 基础测试、迁移和隐私保护。

### P1

- 冲突与过期治理；
- Skill 提炼和管理；
- Wiki 文档导入；
- 第二 Agent 适配器；
- 召回解释与质量仪表盘。

### P2

- CodeGraph；
- 多设备同步；
- 可选远端部署；
- 高级插件生态；
- 多用户或家庭空间。

## 6. 验收指标

### 产品指标

- 首次安装至可用召回 ≤ 15 分钟；
- 普通用户可通过一条命令完成安装、初始化、启动和健康检查；
- 关键工作流无需直接操作数据库；
- 100% 派生记忆能定位到原始来源；
- 用户能在界面完成修改、拒绝、合并、导出和删除。

### 质量指标

- 建立不少于 100 个带期望答案的个人记忆评测样本；
- 分别记录 Recall@K、错误注入率、过期记忆命中率和无答案拒答率；
- 召回上下文严格受字符/token 预算控制；
- 核心 API、迁移和级联删除具备自动化测试；
- 关键数据操作有结构化审计，但日志不记录敏感正文。

### 性能目标（MVP 初始值）

- 1 万条 Atom 本地搜索 P95 < 500 ms（不含外部模型调用）；
- 普通召回 P95 < 1 s；
- 后台提炼失败可重试且不阻塞已有记忆查询。

这些数值需在 Phase 0 用目标设备校准，而不是作为未经验证的上游能力承诺。

## 7. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 上游快速演进导致 fork 漂移 | 少改核心、扩展点优先、固定基线、按月同步并记录冲突 |
| 错误记忆污染后续会话 | 待审阅状态、置信度、来源追溯、冲突与失效机制 |
| 本地优先但模型调用外发数据 | 明示 provider、字段脱敏、离线模式、按来源授权 |
| 删除只删索引不删原文 | 设计级联删除清单并做恢复后复测 |
| 检索过多造成上下文污染 | 分层召回、RRF、阈值、条数/字符/超时预算 |
| 早期范围过大 | MVP 只做 Chat Memory 闭环，Skill/Wiki/CodeGraph 按证据开放 |
| 名称或品牌混淆 | 发布前检索，突出独立二开，保留上游归属 |

## 8. 工程决策门

编码前必须确认：

1. 首发 Agent 是 Codex、通用 MCP，还是 CodeBuddy；
2. 默认推理使用本地模型还是允许配置远端模型；
3. 上游采用稳定 tag 还是当前团队版分支；
4. 事实源采用“数据库为主”还是“可读文件为主、索引可重建”；
5. MVP 是否只含 Chat Memory，还是必须同时交付 Skill/Wiki。

建议默认答案：**通用 MCP + 可配置模型（默认不外发）+ 稳定 tag + 可读资产可导出且索引可重建 + MVP 只做 Chat Memory。**

## 9. 第一迭代任务拆分

1. 创建 `upstream` remote，选择并记录基线 SHA。
2. 保留上游 LICENSE，新增 THIRD_PARTY_NOTICES。
3. 在干净机器/容器跑通上游服务和测试。
4. 固化一个会话导入与召回的黄金样例。
5. 绘制当前上游模块依赖与数据流，不先做目录级重构。
6. 定义 PersonalMemory 配置、数据目录和 API 边界。
7. 实现单用户启动流程和健康检查。
8. 实现记忆收件箱最小数据模型与列表页原型。
9. 为导出、彻底删除、召回预算补自动化验收测试。
10. 复盘实测结果后再冻结 Phase 1 详细技术方案。

## 10. 版本策略

- `main`：始终可运行；
- 功能分支：短生命周期，小步合并；
- 上游同步：单独分支完成构建、迁移和回归测试后合入；
- PersonalMemory 自有模块使用独立命名空间，避免修改上游公共接口；
- 每次升级记录：上游基线、数据库 schema、迁移路径、已知不兼容项。
