# M0.4 standalone Gateway 黄金链路

- 状态：completed
- 日期：2026-08-07
- 范围：隔离运行 standalone Gateway，验证 L0 → L1 → 搜索 → 来源 → 重启恢复

## 自动化链路

`npm run test:golden` 执行以下步骤：

1. 创建系统临时数据目录、动态 loopback 端口和临时配置；
2. 启动只监听 `127.0.0.1` 的 OpenAI-compatible mock server，不访问外部模型；
3. 启动 standalone Gateway 并检查 `/health`；
4. 通过正式 TypeScript SDK 写入一轮固定 L0 会话；
5. 查询并使用 SQLite FTS 搜索 L0；
6. 由真实 pipeline worker 触发 L1，经过真实 AI SDK/provider HTTP 协议调用 mock server；
7. 搜索 L1，并检查可读 JSONL 中保留 `source_message_ids` 与原始消息 ID；
8. 停止并重启 Gateway，再次查询 L0 和 L1，证明 SQLite/JSONL 数据持久化；
9. 停止全部进程并删除临时目录。

## 实施中发现并修复的问题

- TypeScript SDK 把外部 Undici Agent 交给 Node 内置 fetch，版本协议不兼容，本地请求报 `UND_ERR_INVALID_ARG`；现仅在显式关闭 HTTPS 证书校验时创建 dispatcher。
- SDK 原先默认跳过 TLS 证书校验；现改为默认验证，开发者必须显式选择不安全模式。
- Gateway 进程关闭沿用了 StorePool 面向在线驱逐的 30 秒宽限期，导致每次重启等待约 30 秒；进程关闭路径现将宽限期设为 0。
- HTTP server 关闭会主动清理空闲连接，并在 2 秒后结束残留连接，避免升级和卸载无限等待。
- Gateway 现在先停止 HTTP listener 并排空连接，再销毁 worker、state、store 和 core；黄金链路并发验证 stop 开始后健康请求不可再进入。
- Gateway 暴露只读监听地址，测试使用端口 `0` 由操作系统原子分配，消除端口探测与实际绑定之间的竞争窗口。
- SDK 增加幂等 `close()` 释放显式不安全 HTTPS 模式创建的 Undici Agent；SDK 与根项目最低 Node 版本统一为 22.19.0。
- 测试对 Gateway 模块采用配置完成后的动态导入，日志写入隔离目录，不触碰 `/data/log` 或用户数据。
- 测试清理使用 `allSettled` 与 `finally`，初始化或断言失败仍会尝试关闭 Gateway、mock server、恢复环境变量并删除临时目录。

## 验证结果与性能基线

- 黄金链路连续多次通过；最终完整门禁中的黄金链路测试耗时约 5.4 秒。
- 首次启动实测约 1.7 秒；健康检查约 2 毫秒；L0 FTS 搜索约 3 毫秒；本地 mock L1 pipeline 约 19 毫秒。
- 上述数字来自 macOS 14.5 arm64、Node 22.22.1 的开发设备，只是环境基线，不是产品性能承诺。
- 根 build 与 10 项常规测试通过；TypeScript SDK build 与 35 项测试通过；Python SDK 34 项测试通过；两处 npm audit 均为 0。
- 已知 P3：Node 当前将内置 SQLite 标记为 experimental；不影响本次链路，发布支持矩阵需继续跟踪。

## 审查重点

- 测试是否可能连接 loopback 以外的地址；
- 临时目录、端口和进程能否在失败路径可靠清理；
- L1 是否由真实 pipeline 触发，而不是直接伪造数据库记录；
- 来源验证、重启恢复和性能阈值是否具有确定性；
- SDK TLS 行为变更是否有充分回归保护和文档说明。

## 独立审查结论

- 最终结论：P0 = 0、P1 = 0、P2 = 0，可以提交。
- 已确认 TLS 安全默认、SDK dispatcher 生命周期、Gateway 关闭顺序、动态端口、L1 同记录来源断言、重启持久化、loopback 边界和失败清理均符合本步骤要求。
- 保留 P3：`HttpTransportRuntime` 是低层测试或高级注入接口，后续公开 API 文档应说明普通用户无需使用。
