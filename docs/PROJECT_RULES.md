# PersonalMemory 项目执行规则

> 状态：生效  
> 建立日期：2026-08-06  
> 用途：作为后续产品讨论、架构设计、编码、测试和评审的默认执行依据。

## 1. 规则维护机制

1. 用户明确确认的原则、边界和技术决策，应及时写入本文档。
2. 后续聊天中形成的稳定结论，如果会反复影响产品或开发执行，也应主动补入本文档。
3. 临时想法、候选方案、尚在比较的技术选型不得直接升格为规则，应放入“待决策事项”。
4. 新规则与旧规则冲突时，不静默覆盖：应说明冲突，记录替代关系和变更原因。
5. 项目文档保存完整规则和依据；Codex 项目记忆只保存关键结论、讨论进度及文档位置。
6. 规则变更应与相关代码在同一次变更中更新，避免文档和实现长期不一致。

## 2. 产品定位

1. PersonalMemory 是基于 TencentDB-Agent-Memory 二次开发的个人 AI 记忆产品。
2. 产品聚焦单用户、本地优先场景，不做上游团队版的简单换皮或功能删减版。
3. 核心价值是让个人记忆在不同 Agent、项目和会话之间安全沉淀、检索、审阅、纠错和迁移。
4. MVP 首先验证 Chat Memory 闭环：会话捕获/导入、L0–L3 提炼、召回、人工纠错、导出和彻底删除。
5. Skill、Wiki、CodeGraph 根据真实需求分阶段开放，不要求 MVP 同时交付。
6. MVP 以产品化交付为目标，不以演示可运行为完成标准；优先保证安装、数据安全、恢复能力、可维护性和升级路径。
7. MVP 首发支持单用户、macOS 与 Linux；完整管理 L0/L1，L2/L3 首版以查看和来源追溯为主，复杂结构化编辑后置。

## 3. 数据与隐私

1. 本地优先，用户拥有原始数据、派生记忆和完整导出能力。
2. 默认私密；任何外发、共享或云端模型处理都必须明确配置并让用户可感知。
3. 记忆必须可见、可改、可拒绝、可合并、可失效、可删除。
4. 派生记忆必须能追溯到原始来源和提炼链路。
5. 删除必须覆盖原始证据、派生资产、检索索引、缓存及备份策略定义的相关副本，不能只删除界面记录。
6. 召回采用渐进披露和预算控制，避免把全部历史无差别注入上下文。
7. 错误或冲突记忆不得静默覆盖现有有效记忆，应保留状态和替代关系。

## 4. 上游与架构

1. 技术栈向 TencentDB-Agent-Memory 选择性靠拢：核心同栈、接口兼容、产品层独立。
2. 首个上游代码基线固定为 TencentDB-Agent-Memory `v1.0.1`，即 `feat/server` 代码线；不得误用 `main` 的 0.x 插件线或 `feat/server_team` 的 v2 团队产品线作为基线。
3. `feat/server` 作为后续上游修复的跟踪分支；未发布提交必须经过差异审查、构建和回归测试后选择性引入。
4. `v2.0.0` / `feat/server_team` 只作为 Memory Hub、Web Panel、Skill、Wiki、CodeGraph 等能力的设计与实现参考，不直接继承其多租户和团队架构。
5. 不重写上游记忆内核；L0–L3 管线、核心数据模型和检索机制优先继承上游。
6. PersonalMemory 自有能力通过扩展层、独立命名空间、独立数据表和版本化 API 实现。
7. 少改上游核心，优先使用扩展点；固定上游基线并记录版本、提交 SHA 和迁移路径。
8. 上游同步必须在独立分支完成构建、迁移及回归测试后再合入主分支。
9. MVP 不引入没有个人场景依据的多租户、复杂 RBAC、Redis、ClickHouse 或企业监控依赖。
10. 第一阶段不为了“架构先进”拆分额外微服务，优先保证本地部署和维护简单。

## 5. 已确认技术栈

1. 主要语言：TypeScript。
2. 运行时：Node.js 22.19.0 或更高版本。
3. API：Hono + Zod。
4. Web 前端：React + Vite；数据请求和路由分别优先采用 TanStack Query 与 React Router。
5. 本地数据库：SQLite。
6. 检索：SQLite FTS/BM25 + sqlite-vec + RRF 融合排序。
7. 测试：Vitest；端到端界面测试采用 Playwright。
8. Agent 接入：通用 MCP 优先，同时保持上游 HTTP/SDK 兼容。
9. 模型接口：OpenAI-compatible，并允许配置本地模型；默认行为不得在用户不知情时外发数据。
10. 初期部署：Docker Compose 或等价的本地服务组合；待核心闭环稳定后再评估 Tauri 桌面封装。
11. 第一版不采用 Electron/Tauri 作为前置条件，先验证本地服务 + Web UI。

## 6. 工程与质量

1. `main` 始终保持可运行；功能分支短生命周期、小步合并。
2. 引入上游代码必须保留原始 LICENSE、版权和第三方归属说明，不暗示腾讯官方背书。
3. 数据库 schema 必须版本化；升级必须提供迁移路径，高风险迁移应支持回滚或备份恢复。
4. 关键闭环必须有自动化验收：捕获、提炼、召回、纠错、导出、恢复和彻底删除。
5. 性能数字必须经过目标设备实测，不把上游数据或设计目标直接当作 PersonalMemory 的能力承诺。
6. 日志默认不记录记忆正文、密钥或其他敏感内容；必要诊断信息应脱敏。
7. 索引应能够从可导出的事实资产重建，避免不可读数据库成为用户数据的唯一载体。
8. 开发严格按 [实施计划](IMPLEMENTATION_PLAN.md) 的步骤推进；每个步骤都必须经过实施前检查、验证检查和代码审查，全部通过后才能提交并进入下一步。
9. 代码审查发现阻断问题时不得带病进入后续步骤；修复后必须重新执行受影响的检查。
10. 每个步骤的检查和审查结论应留在提交信息、开发记录或可追溯的审查记录中，不能只口头宣布通过。

### 6.1 Git 提交规则

1. 后续开发过程中，完成一个边界清晰、可独立验证的变更单元后，应主动执行 Git commit，无需每次等待用户提醒。
2. 提交前必须检查变更范围、敏感信息、格式及与本次任务相关的测试；不得把无关修改混入同一提交。
3. 提交应保持原子性：一个提交只表达一个主要意图，文档和实现可在同一功能提交中同步更新。
4. 提交标题采用 `<type>: <description>` 格式；描述简洁说明结果，默认使用中文，不以句号结尾。
5. 允许的 `type` 及用途：
   - `feat`：新增功能；
   - `fix`：修复缺陷；
   - `perf`：提高代码性能；
   - `style`：只修改代码格式，不改变行为；
   - `refactor`：既非功能新增也非缺陷修复的代码重构；
   - `test`：新增或更新测试；
   - `ci`：持续集成、部署配置或相关服务单元变更；
   - `docs`：用户文档或开发文档更新；
   - `chore`：构建流程、依赖管理或辅助工具等其他变更。
6. 不得在 commit 标题、正文、作者、共同作者或其他元数据中添加 `Codex`、`Claude`、`AI generated` 等 AI 生成标记。
7. 不擅自改写已共享的 Git 历史；除非用户明确要求，不执行 rebase、amend、force push 等会改变既有提交的操作。
8. 是否推送远端与本地 commit 分开处理；除非用户明确授权，不自动执行 Git push。

### 6.2 安装与首次使用

1. 完整产品必须以“一条命令完成安装并进入可用状态”为目标，不要求普通用户手工安装多个运行时、编辑多份配置或理解内部服务拓扑。
2. 安装命令应完成环境检查、组件获取、配置初始化、服务启动和健康检查，并给出明确的成功结果及下一步入口。
3. 必填密钥或模型配置无法自动获得时，安装流程应提供交互式引导或清晰的单一配置入口，不能以隐式默认值外发用户数据。
4. 安装过程应幂等、可诊断；重复执行不得破坏已有数据，失败时应说明原因和恢复方法。
5. 同时提供升级、备份恢复和卸载能力；卸载程序不得在未明确确认的情况下删除用户记忆数据。
6. 发布验收必须覆盖干净环境的一条命令安装测试，并记录支持的平台、架构、耗时和已知限制。

## 7. 命名与发布

1. `PersonalMemory` 作为当前工程名和 MVP 名称继续使用。
2. 它尚未确定为最终商业品牌；正式发布前检查商标、域名、GitHub、npm/PyPI 和应用商店重名情况。
3. 若采用独特主品牌，可保留 “Personal AI Memory” 或“个人 AI 记忆工作台”作为品类副标题。
