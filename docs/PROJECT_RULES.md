# PersonalMemory 项目执行规则

> 状态：生效  
> 建立日期：2026-08-06  
> 用途：作为后续产品讨论、架构设计、编码、测试和评审的默认执行依据。

## 1. 规则维护机制

1. 用户明确确认的原则、边界和技术决策，应及时写入本文档。
2. 后续聊天中形成的稳定结论，如果会反复影响产品或开发执行，也应主动补入本文档。
3. 临时想法、候选方案、尚在比较的技术选型不得直接升格为规则，应放入“待决策事项”。
4. 新规则与旧规则冲突时，不静默覆盖：应说明冲突，记录替代关系和变更原因。
5. 项目文档保存完整规则和依据；Codex 项目记忆只保存关键结论、讨论进度及文档位置。
6. 规则变更应与相关代码在同一次变更中更新，避免文档和实现长期不一致。

## 2. 产品定位

1. PersonalMemory 是基于 TencentDB-Agent-Memory 二次开发的个人 AI 记忆产品。
2. 产品聚焦单用户、本地优先场景，不做上游团队版的简单换皮或功能删减版。
3. 核心价值是让个人记忆在不同 Agent、项目和会话之间安全沉淀、检索、审阅、纠错和迁移。
4. MVP 首先验证 Chat Memory 闭环：会话捕获/导入、L0–L3 提炼、召回、人工纠错、导出和彻底删除。
5. Skill、Wiki、CodeGraph 根据真实需求分阶段开放，不要求 MVP 同时交付。
6. MVP 以产品化交付为目标，不以演示可运行为完成标准；优先保证安装、数据安全、恢复能力、可维护性和升级路径。
7. MVP 首发支持单用户、macOS 与 Linux；完整管理 L0/L1。L2/L3 首版提供查看和诚实的来源可用性状态，不承诺当前上游格式无法证明的完整下钻链；复杂结构化编辑与完整 L3→L2→L1→L0 来源链后置。

## 3. 数据与隐私

1. 本地优先，用户拥有原始数据、派生记忆和完整导出能力。
2. 默认私密；任何外发、共享或云端模型处理都必须明确配置并让用户可感知。
3. 记忆必须可见、可改、可拒绝、可合并、可失效、可删除。
4. 派生记忆必须能追溯到原始来源和提炼链路。
5. 删除必须覆盖原始证据、派生资产、检索索引、缓存及备份策略定义的相关副本，不能只删除界面记录。
6. 召回采用渐进披露和预算控制，避免把全部历史无差别注入上下文。
7. 错误或冲突记忆不得静默覆盖现有有效记忆，应保留状态和替代关系。
8. 产品配置优先级固定为安全默认值、配置文件、环境变量；未知配置项必须拒绝，密钥只从环境变量加载并在日志与序列化结果中脱敏。
9. Gateway/Web 默认仅监听 loopback；非 loopback 必须显式启用认证。模型访问与遥测默认关闭，远程模型必须使用 HTTPS、显式 origin allowlist，并在启用前披露 provider、目标和发送字段。
10. 本地数据目录默认使用操作系统用户数据目录，以 `0700` 创建；禁止文件系统根目录、符号链接路径和对误选既有目录的隐式覆盖或权限修改。
11. PersonalMemory Gateway 对外只提供版本化个人 API；浏览器仅在 loopback 使用短期 session + CSRF，MCP/SDK 使用 Bearer。未配置认证时不得开放记忆读写。
12. Gateway 到腾讯上游只允许编译期列明的记忆路由，并通过不读取环境代理的 loopback 直连传输；不得暴露上游 `instance/destroy` 为个人数据彻底删除。

## 4. 上游与架构

1. 技术栈向 TencentDB-Agent-Memory 选择性靠拢：核心同栈、接口兼容、产品层独立。
2. 首个上游代码基线固定为 TencentDB-Agent-Memory `v1.0.1`，即 `feat/server` 代码线；不得误用 `main` 的 0.x 插件线或 `feat/server_team` 的 v2 团队产品线作为基线。
3. `feat/server` 作为后续上游修复的跟踪分支；未发布提交必须经过差异审查、构建和回归测试后选择性引入。
4. `v2.0.0` / `feat/server_team` 只作为 Memory Hub、Web Panel、Skill、Wiki、CodeGraph 等能力的设计与实现参考，不直接继承其多租户和团队架构。
5. 不重写上游记忆内核；L0–L3 管线、核心数据模型和检索机制优先继承上游。
6. PersonalMemory 自有能力通过扩展层、独立命名空间、独立数据表和版本化 API 实现。
7. 少改上游核心，优先使用扩展点；固定上游基线并记录版本、提交 SHA 和迁移路径。
8. 上游同步必须在独立分支完成构建、迁移及回归测试后再合入主分支。
9. MVP 不引入没有个人场景依据的多租户、复杂 RBAC、Redis、ClickHouse 或企业监控依赖。
10. 第一阶段不为了“架构先进”拆分额外微服务，优先保证本地部署和维护简单。

## 5. 已确认技术栈

1. 主要语言：TypeScript。
2. 运行时：Node.js 22.19.0 或更高版本。
3. API：Hono + Zod。
4. Web 前端：React + Vite；数据请求和路由分别优先采用 TanStack Query 与 React Router。
5. 本地数据库：SQLite。
6. 检索：SQLite FTS/BM25 + sqlite-vec + RRF 融合排序。
7. 测试：Vitest；端到端界面测试采用 Playwright。
8. Agent 接入：通用 MCP 优先，同时保持上游 HTTP/SDK 兼容。
9. 模型接口：OpenAI-compatible，并允许配置本地模型；默认行为不得在用户不知情时外发数据。
10. MVP 首发部署使用本机 Node.js 受管进程组合，暂不使用 Docker；待核心闭环稳定后再评估内置运行时、系统用户服务或 Tauri 桌面封装。
11. 第一版不采用 Electron/Tauri 作为前置条件，先验证本地服务 + Web UI。
12. 首发 Agent 接入采用通用 MCP；具体 Agent 只作为客户端适配层，不成为产品核心依赖。
13. SQLite 是运行时权威状态；可读导出必须版本化并可供人工阅读与校验。由可读导出重建新安装和检索索引是长期方向，不属于当前 MVP；MVP 的跨安装迁移与灾难恢复只承诺已验证的完整备份。
14. Web 管理端使用个人语义，不引入团队、成员、组织、租户或工作区概念；加载、错误和空状态必须给出明确反馈与下一步，主要路径必须支持键盘导航、可见焦点和减少动画偏好。
15. 本地开发统一使用根目录 `npm run dev`；启动器不得隐式下载安装，必须在启动前检查端口、健康确认后报告入口，并在正常或异常退出时清理子进程和本轮隔离数据，不得触碰正式用户数据。
16. 会话捕获和批量导入必须使用持久化幂等键与轮次级状态；相同键不同载荷拒绝，重试不得重复发送已成功轮次，进程中断必须恢复为可诊断且可重试状态。
17. 导入消息只接受成对的 user/assistant 角色并设置会话、消息和任务上限；模型 provider 启用时，必须先披露 provider、目标 origin 和发送字段，并在上游捕获前获得显式确认。
18. 统一召回必须在调用前按层级过滤，并在合并后再次强制总条数、字符、估算 token 和统一截止时间预算；单层失败应显式降级，不得泄露正文到日志或伪造跨层可比分数。
19. 未经代码和测试证明为召回前执行的元数据过滤不得暴露为产品能力；L2/L3 只允许经编译期白名单的读取与整文件写入路由，不开放删除或实例销毁。此规则在 M2.5 以受控写入替代 M2.3 的只读边界，原因是实施计划已进入人工纠错步骤；复杂结构化编辑仍后置。
20. 记忆浏览界面必须区分原始对话与推断/沉淀内容；只有真实可达的引用才能展示为来源链，缺失引用时必须明确标注“来源未记录”，不得用相似搜索结果冒充来源。
21. PersonalMemory 状态表是浏览和召回的权威抑制层；失效或删除 tombstone 必须在重启、上游重建索引或同 ID 数据再次出现后继续阻止记忆复活。失效记忆不得通过普通编辑隐式恢复，删除 tombstone 在 M2 不可恢复。
22. M2 的受控删除仅支持 L1：先持久化删除 tombstone，再尽力删除上游 L1 索引；界面和 API 必须明确它不删除原始对话、L2/L3 派生资产、日志、导出物或备份，也不等同于 M3.4 的可验证级联删除。
23. M2 可移植数据操作只支持统一数据根下的本地 SQLite 拓扑，并必须在 Gateway 停止后执行。可读导出包含 L0–L3、来源原始字段和 PersonalMemory 状态；备份采用显式资产清单、逐文件 SHA-256 和 fail-closed 未分类资产检查，永不包含配置、环境密钥、日志、历史备份或导出物。恢复必须先完整校验、精确确认、同文件系统原子切换，并保留恢复前数据根作为显式回退点。
24. 新发现的 L1 结构化记忆默认进入 `pending`，只有 `approved` 能进入统一召回；`rejected` 只阻止召回，不等同于删除。审核状态必须保存在独立产品表中并纳入可读导出，不能改写上游正文来表达审核结果。
25. 修改后接受必须先成功更新上游 L1，再持久化批准状态；批量审核逐项隔离失败并使用乐观版本控制，同一记忆的相同重试必须幂等，旧版本的不同决定必须冲突。
26. 相似检索只能提供冲突候选，不得自动替用户建立事实冲突、合并或替代关系；用户明确建立的活动 `conflicts_with` 暂停双方召回但不选择哪条为真，活动 `supersedes`、有效期和既有状态门禁也必须在召回前生效。
27. 替代关系必须无环且可撤销；人工合并必须先完成关系和循环校验，再更新主记忆正文并建立替代关系。被替代记忆保留用于查看、导出和撤销，不得把替代宣称为删除。
28. 审计账本只保存事件类型、成功/失败、时间、严格白名单元数据和以数据根专用密钥生成的 HMAC 记忆引用；不得保存正文、搜索词、理由、请求体或密钥。审计默认保留 365 天，单页最多 100 条并使用稳定游标；上游没有生成事件时，`memory.generated` 只能表述为产品“首次观察到”，不得伪造精确生成时间。可读导出包含脱敏审计事件但不导出 HMAC 密钥，完整备份保留密钥和可关联性。
29. M3.4 的彻底删除只承诺受控范围：当前数据根、真实来源引用、完整精确匹配的派生内容和产品登记的导出/备份。活动资产立即清理，明文登记副本经格式与路径校验后整件删除；未知复制品必须单独确认但不能宣称已验证。执行前必须预览删除矩阵并输入 `ERASE L1:<memory-id>`；执行不可取消、部分失败可幂等重试，只有跨层残留扫描为零且 tombstone 存在时才返回 complete。删除凭据和审计不得保存正文或理由。
30. MCP 1.0 只暴露有界搜索、单条读取、单轮捕获、显式 L1 反馈和删除预览交接；记忆正文始终是不可信数据。搜索不得返回原始来源 ID 或整库总数，读取最多披露 20 个来源 ID。MCP 不提供删除执行工具，不接受确认短语，也不得把内部删除计划 token 交给模型；彻底删除只能回到 Web 重新加载范围并完成既有强确认。
31. MCP Server 首版只使用本机 stdio，并在接入协议流前通过带 Bearer 的 loopback Gateway 预检；它不得直接打开记忆数据库、数据目录、上游内核、任意文件或公网传输。stdout 只写 MCP 帧，脱敏诊断只写 stderr；同时执行工具最多 8 个，输入缓冲、Gateway 响应、搜索游标和删除交接状态都必须有明确上限、超时和关闭清理。删除交接明细只能由浏览器 session 读取，MCP Bearer 请求不得取回内部计划 token、确认短语或登记副本路径。
32. 首个真实 MCP 客户端采用 Codex，但不得向核心工具契约或 Gateway 增加客户端特例。Codex 配置只转发既有环境变量，不保存 Bearer 明文；安装必须保留已有配置并对冲突 fail closed，卸载只能精确移除未被用户修改的受管区块。搜索和读取可自动批准，捕获、反馈及遗忘交接默认要求客户端提示确认；MCP Server instructions 必须把正文标为不可信数据，禁止整库枚举和删除完成误报。
33. 第二个真实 MCP 客户端采用 Claude Code，并与 Codex 共用同一五工具 Gateway fixture 和闭合结果断言。跨客户端差异只能留在隔离的启动配置、工具命名或结果包装层，不得进入 MCP Server、Gateway 或记忆契约；测试可在独立 HOME、严格 MCP 配置和工具白名单下自动批准五工具，但面向用户的捕获、反馈和遗忘交接仍必须默认提示确认。
34. 产品安装器首版只支持 macOS/Linux 和 Node.js 22.19.0 以上的源码分发物安装；依赖已存在时允许断网安装，缺失依赖时只能使用锁文件获取。安装必须先检查端口再写状态，生成的认证凭据只保存在 `0600` 本地文件且不进入回执或输出；核心 Gateway、产品 Gateway 与 Web 仅监听 loopback，模型和遥测保持关闭。首次和重复安装都必须验证四个受管进程、三个 HTTP 健康入口、Hook worker 脱敏维护状态以及非降级 L0/L1 召回。残缺或部分停止的回执必须 fail closed，不自动覆盖数据或猜测清理范围；只有私有回执校验通过且四个受管进程全部停止时，才允许重新安装，未显式指定的端口必须沿用回执，显式端口变更必须保留旧回执直至新服务健康且替代回执原子提交成功。
35. 运行回执、日志和认证凭据必须位于记忆数据根之外的私有状态目录，避免进入完整备份。源码升级只使用当前本地仓库，不下载或执行远程脚本；升级前必须严格校验受管回执、要求可用空间至少为受管数据两倍加 128 MiB、构建目标版本、停止受管进程、创建并校验完整备份，再显式迁移、重启并验证三个健康入口和非降级 L0/L1 召回。升级成功仍保留备份；任何迁移或启动失败必须从已校验备份恢复数据，服务保持停止且不得恢复含过期 PID 的旧回执；恢复不完整必须 fail closed，不得隐藏为成功。
36. 生命周期命令只能从私有普通文件回执解析受管状态和数据绝对路径，并拒绝根目录、符号链接、宽权限目录、状态/数据嵌套和路径扩张。备份与恢复必须先停止服务并移除过期回执，验证完成后重新安装启动；失败也应尽力恢复已有数据服务。无回执重启必须严格校验并复用已有 `0600` 凭据，不能覆盖或静默轮换。卸载默认只移除状态目录并保留全部记忆数据；清除数据必须同时提供 `--purge-data` 和精确的 `DELETE <绝对数据根>` 确认，且确认必须在停止进程或删除任何文件之前校验。
37. MVP 首发版本使用独立 annotated Git tag `personalmemory-v0.1.1` 固定，不得与上游标签 `v1.0.1` 混用或移动；用户可按该 tag 克隆安装。版本化源码压缩包仍作为可离线校验的正式分发物，不发布 npm 公共包。发布物必须包含固定顶层目录、上游 LICENSE、第三方依赖归属清单、机器可读发布清单和一条命令安装入口，并提供独立 SHA-256 校验文件；不得包含 `.git`、依赖缓存、构建输出、日志、密钥或用户数据。安装只通过锁文件获取依赖，发布验收必须从该真实分发物完成校验、解包、安装、非降级召回、升级/恢复和卸载矩阵。
38. 自动记忆生命周期是 MVP 核心体验：用户首次分别授权自动召回和自动本地捕获后，Agent 应在用户提示提交前自动召回，在主 Agent 成功完成一轮后自动捕获成对的原始 user/assistant 文本，不要求用户逐轮要求“搜索”或“保存”。
39. 自动 Hook 必须通过 PersonalMemory Gateway 使用统一审核、治理和预算门禁；自动召回只注入 `approved` 且有效的记忆，不得注入 `pending`/`rejected` L1 或绕过产品层读取上游。自动捕获不得包含 system/developer 指令、工具调用/输出、附件和已注入记忆。
40. 自动捕获授权只覆盖已声明的生命周期 Hook；Agent 主动调用 MCP 捕获、反馈和遗忘交接仍逐次确认。新 L1 继续默认 `pending`，纠错、合并、冲突/替代和删除仍由用户明确决定，彻底删除仍只能在 Web 强确认。
41. 本地捕获授权与模型外联授权分离。未获得有效模型授权时允许保存 L0 但必须暂停需要外联模型的提炼；provider、origin 或发送字段变化后必须重新同意。产品 Gateway 与上游核心必须共享一个权威模型/出站门禁，不能出现界面显示关闭而上游仍尝试外联。
42. 自动采集必须在 L0 落盘前执行服务端权威策略，至少支持全局及按 Agent、项目/工作目录、来源暂停或排除，并提供敏感内容规则、用户可见状态和审计。召回失败不得阻断 Agent；捕获失败必须进入有界私有 outbox、有限重试并显式告警，不得静默丢失或无界重试。
43. Hook 事件必须使用稳定的 Agent/session/turn 幂等标识；重复事件不得重复写入，相同键不同载荷必须冲突。普通 command Hook 不得自行再次调用 Agent；自动召回上下文及后台提炼 token 必须分别受预算和可观测性约束。
44. 自动 Hook 公共契约以 `UserPromptSubmit` 的原始 prompt 和同 turn `Stop` 的最终 assistant 文本为事实源；不得依赖格式不稳定或异步滞后的 transcript 重建当前轮。Codex 使用原生 `turn_id`，Claude Code 优先使用 `prompt_id`，旧版本由客户端 Adapter 生成不含正文的稳定标识；公共请求必须显式声明非 subagent，捕获幂等键必须使用安装级私钥 HMAC 且不得包含正文。召回最多注入 5 条、4,000 字符、估算 1,000 token 并在 1 秒内 fail-open；客户端配置存在或 Hook 已信任不等同于产品授权，授权和策略 revision 仍由 Gateway 校验。
45. 自动 Hook 捕获不得在模型外联门禁收口前直接复用可能触发模型处理的上游 `/capture`。Gateway 必须先停在显式注入的同步本地捕获边界，生产默认关闭；sink 只能使用账本传入的活动 SQLite 事务写入 L0，并同步返回唯一提交凭证，使本地写入与幂等落账同事务提交或整体回滚，异步 Promise 和事务外副作用不得视为成功。只有 M4.6 证明 L0 可本地落盘且未授权时不会提炼或外联后，才能接入生产 capture sink。持久化幂等账本只保存 HMAC 键、独立载荷摘要、状态和时间戳，不保存正文、cwd 或客户端配置。
46. 客户端 Hook 的明文 turn 暂存必须位于私有、无符号链接路径，采用带 owner 存活校验和恢复互斥的跨进程锁、原子替换、1 小时逻辑 TTL、最多 128 条和 4 MiB 总上限；每次访问必须先把过期正文从磁盘清除，正式安装接入受管常驻 Hook worker 后还必须定时清扫无后续事件的过期记录。容量回收不得驱逐活动认领或在未保存新 turn 时返回成功。`Stop` 只能通过带随机 token 和短租约的 claim 读取，Gateway 捕获成功或请求已进入持久 outbox 后才 acknowledge 删除；崩溃后允许租约到期重领，旧 token 不得删除或释放新认领。同一原生 turn 的完全相同前置事件视为重试，不同正文或 cwd 必须冲突并保留首条；旧版 Claude 只在当前待配对回合内复用随机且不含正文的 turn 标识，完成后下一回合必须生成新标识。
47. Hook Runtime 只能以 Bearer 认证访问显式 loopback HTTP Gateway，禁止凭据、重定向和非 loopback origin；UserPromptSubmit 从 turn 暂存开始必须共享 1 秒绝对 deadline，Gateway 只能使用剩余预算，捕获 HTTP 调用不得超过 1 秒，召回与捕获响应正文分别最多 16 KiB 与 4 KiB。只有网络/超时或 HTTP 502/503/504 可进入 outbox，鉴权、契约、冲突和策略结果必须按终态处理或 fail-open 报警，不得无限重试。outbox 必须位于私有无符号链接目录，固定最多 64 条、单条 256 KiB、正文 TTL 24 小时、claim 名义租约 30 秒；最多尝试 5 次，退避固定为 1 秒、5 秒、30 秒、60 秒，耗尽后保留失败状态至 TTL 并向状态接口暴露脱敏 backlog。并发入队与 flush 必须原子且同一项只能由一个消费者投递；只有 Gateway 返回终态、不可重试协议终态或 outbox 已持久接纳后才 acknowledge turn，outbox 持久化失败必须 release。前台 Hook 不得同步 flush backlog；任何 Hook 失败都只能返回允许客户端继续的空输出，固定不可信警告与召回正文只能进入客户端 `additionalContext` 通道且共同受字符/token 预算约束。

48. 正式安装必须用私有回执管理 Codex hooks.json 和 Claude Code settings.json，并保留无关配置。目标事件冲突、受管定义被编辑或复制、回执缺失或路径扩张时必须 fail closed。
    命令、配置、回执、状态和日志不得包含 Bearer、安装级 HMAC 私钥或正文。
    Codex 初装和定义升级必须报告 installed_untrusted；只有当前精确定义实际产生该客户端首事件回执后才可报告 healthy。不得绕过 Hook 信任。
    安装必须启动维护 worker，至少每分钟物理清扫过期 turn、维护 outbox，并只向 lifecycle/doctor 暴露脱敏状态；前台 Hook 不承担维护。
    升级只替换回执证明未修改的旧定义并清除旧事件回执；卸载只移除当前受管定义。
    隔离 HOME 验收使用安装器生成的双客户端配置和本地 Gateway fixture；可用的真实客户端还必须解析该配置。

49. PersonalMemory 受管启动的上游模型环境只能由产品模型配置派生，不得直接继承宿主的 `TDAI_LLM_*` 或 `MEMORY_TENCENTDB_LLM_*` 地址、密钥和模型。产品模型关闭时必须显式向上游设置最终禁用门禁，并在启动前移除继承的模型配置；受管上游 Gateway 进程可达的 LLM Runner 和直接模型客户端还必须在发起请求前再次检查该门禁。旧 OpenClaw 插件的独立 offload 入口不在 PersonalMemory 受管进程中，继续属于上游兼容面而非本步骤的产品配置入口。该门禁只收口模型外联，不代表已完成版本化授权、发送字段披露、生产 Hook capture sink 或全部遥测外联验证。
50. 模型外联授权必须持久化为版本化账本，并精确绑定 provider、目标 origin 和发送字段；当前披露固定包括模型输入、选中的记忆上下文和导入会话消息。任一绑定项变化都使旧授权失效，逐请求 `model_outbound_acknowledged` 不得替代持久授权。模型密钥只保存在 `0600` 私有配置文件中，不进入授权 API 或账本；受管启动仅在当前披露已授权时把单一产品配置映射给上游，并移除代理环境变量，未授权、已撤销、账本缺失或读取失败都必须向上游传递最终禁用状态。授权或撤销后必须重启受管服务才能改变实际上游进程环境；生产 Hook capture sink 仍不在本步骤启用。
51. 生产 Hook 本地捕获只能把契约允许的一对原始 user/assistant 消息同步写入上游 `vectors.db` 的 L0 元数据表，不得调用上游 `/capture`、embedding、提炼或任何网络客户端。Hook 幂等账本与 L0 行必须使用同一 SQLite 连接和同一活动 `BEGIN IMMEDIATE` 事务提交或整体回滚；产品自有 Hook 表使用独立版本化迁移，上游继续唯一拥有 L0 schema，产品启动只做兼容性 preflight。记录 ID 从幂等键和角色单向派生，不保存 cwd。模型未授权时捕获仍可成功落 L0，但受管上游最终模型门禁必须保证不产生 L1–L3 和模型请求。接入生产 sink 不等于开启自动捕获授权；安装默认仍关闭 recall/capture，授权入口与采集策略另行实施。
52. 自动召回和自动本地捕获授权必须由产品 SQLite 中的版本化 Hook 授权账本独立控制，首次安装双关闭；公开认证 API 必须先披露处理数据、时机、目的地和 fail-open 行为，并以 expected revision 防止陈旧覆盖。安装身份由私有 Hook secret 单向派生；身份变化视为新安装，旧授权自动失效且双关闭。Gateway 是授权事实源，受管 worker 在维护和 outbox flush 前通过认证 loopback 请求同步 installation/auth/policy revision，并只在安装身份一致时原子更新私有 runtime 配置；同步失败不得沿用旧 revision 发送或冲刷队列。本步骤的 policy revision=1 仅表示尚无更窄来源排除的全局策略，项目/来源策略、敏感内容规则、保留期与 Web UI 后续独立实施。
53. 自动本地捕获必须在幂等落账和 L0 sink 前经过产品 SQLite 中的版本化采集策略：全局暂停、按 Agent、工作目录树和来源排除均由 Gateway 权威执行；工作目录规则只接受绝对路径、规范化后保存并按目录边界匹配。敏感规则首版固定支持凭据、通过 Luhn 校验的支付卡号和中国居民身份证号类别，命中时整轮不落盘并返回脱敏原因，不记录正文或命中值。策略更新采用 expected policy revision，并同步推进 Hook authorization/policy revision，使旧客户端请求和旧 outbox 条目 fail closed；追加式策略历史必须通过认证 API 可审计。L0/L1 保留期分别允许 1–3650 天或无限期，M4.6.5 只建立权威策略、认证 API 和用户可见状态；自动物理清理不得绕过 M3.4 的索引、派生资产、导出和备份删除矩阵，必须作为后续独立变更接入既有受保护清理器并完成恢复后复测。
54. L0/L1 保留天数是策略配置，不自动构成物理删除授权。自动清理必须另有默认关闭的版本化执行授权，精确绑定披露版本、policy revision、L0/L1 天数和登记副本整件删除方式；任一绑定变化立即失效。有效授权下，L1 使用 retention 专用级联：复用 M3.4 的 tombstone、派生、可读 L1、登记副本、产品元数据和索引顺序，但尚未越过独立 L0 截止点的来源 L0 与可读 L0 必须保留；显式彻底删除仍按 M3.4 删除全部已知来源。独立 L0 必须先清理可读及登记副本，再删除上游元数据/FTS/向量索引，任一前序失败均保留重试定位。每轮必须有界、持久化脱敏 lease/统计并与备份、恢复、升级及彻底删除互斥；只有同一冻结 revision/截止点下复查 `remaining_eligible=0` 才是 `drained`，单批成功仍是 `draining`。未配置或未授权执行时允许沿用 M5.3 备份/恢复但不得宣称满足保留期；有效授权下，备份只接受 `drained`，恢复必须在 staging 中应用当前安装状态目录里的授权与策略封套，并合并恢复前快照的登记副本目录，验证 `drained`、切换成功且处理恢复输入备份后才能启动，失败回滚原数据。M4.6.6.2 完成上述恢复门禁前，生产自动清理保持关闭。
55. 产品创建的可读导出和完整备份必须强制写入 PersonalMemory 数据根之外并登记绝对路径；推荐名称分别为 `personalmemory-export-YYYYMMDD.*` 和 `personalmemory-backup-YYYYMMDD`，名称缺少产品特征时命令返回提醒但不阻止操作。用户自行移动、复制或改名形成的副本无法可靠拦截或追踪，产品必须明确提示且不得计入删除完成声明。
56. M4.7 收窄 MVP 承诺：L0 与带真实来源字段的新 L1 提供可验证来源，旧 L1 及 L2/L3 必须明确显示“来源未记录”，不得用相似检索伪造派生链；可读 JSON/Markdown 导出是长期可读、可校验且不含检索索引的用户资产，MVP 不承诺从它导入或重建安装，跨安装迁移与灾难恢复只使用已验证完整备份。Web 负责浏览、审核、纠错、治理、审计与强确认删除；一条受管 CLI 负责安装、状态、Agent 信任检查、升级、导出、备份、恢复、停止与卸载。普通用户不得被要求直接操作 SQLite 或拼接原始 Gateway API；首版不宣称所有系统管理动作均有 Web 按钮。
57. 产品安装命令使用可重复的 `--agent` 参数选择受管客户端，当前值为 `codex`、`claude-code`、`all` 和 `none`；未传参数时只按 `PATH` 自动检测可用客户端。具体 Agent 可组合并去重，`all`/`none` 不得与其他值组合。重复安装允许调整 Agent 集合，但只能新增所选的受管定义并精确移除回执证明属于 PersonalMemory 且未被修改的旧定义；未选择的 Agent 不参与配置冲突检查，旧双客户端回执必须兼容为两端均已选择。
58. `README.md` 是 PersonalMemory 唯一完整用户入口，集中维护产品功能、安装、首次使用、日常管理、升级、备份恢复、卸载和能力边界。`docs/` 保留发布、架构、计划和实施证据等开发者资料；MVP 尚未对外发布，旧用户手册已直接删除，不得重新复制正文形成双重事实源。
59. 远程一条命令安装使用版本化 `bootstrap-personalmemory.sh`：必须允许显式指定 Git 仓库、严格语义版本 tag、绝对安装目录和可重复 Agent，先取得远端精确 tag 解引用后的提交再浅克隆，并只调用该版本内的正式安装器。已有目录只有在同一仓库、本地 tag、HEAD 与远端 tag 提交三者一致且工作区干净时才可复用；符号链接、未知目录、仓库/版本不一致、远端 tag 被移动和本地修改必须在产品安装前拒绝。引导器暂不安装 Node/npm，不使用 Docker，不跟随移动分支安装产品版本。
60. PersonalMemory 受管 Hook 必须允许与同一 Agent、同一事件中的其他用户 Hook 共存。安装只追加自身定义；状态检查要求每个受管事件精确匹配一个回执摘要；升级先按旧摘要移除自身旧定义再追加新定义；切换 Agent 和卸载只移除精确匹配的一项。其他 Hook 的存在、顺序和内容必须保留；PersonalMemory 自身条目缺失、被修改或重复时继续 fail closed。
61. 源码安装器和远程引导器必须允许分别指定 upstream Gateway、PersonalMemory Gateway 与 Web 端口，默认固定为 `17173`、`17175`、`17177`；端口必须是互不相同的 1–65535 整数。选择结果写入受管回执 URL，并由生命周期和升级沿用；运行中的安装收到不同显式端口时必须拒绝并要求先停止，不得静默忽略或同时启动第二套进程。该默认值替代 M5.9 使用的 `8420`、`8787`、`4173`，用于降低与本机常见开发服务冲突的概率。
62. PersonalMemory 首版普通用户模型配置只支持 `openai-compatible`；Web 只接受 provider、Base URL、API Key 和模型名，密钥只能写入状态目录的 `0600` 私有 `gateway.env`，不得通过查询接口、HTML、日志、回执或错误回显。远程模型必须使用 HTTPS，本机模型只允许 loopback HTTP；模型配置、目标 origin 或发送字段变化后旧授权立即失效。保存、授权、撤销或关闭配置后必须明确显示需要受管重启才能改变上游进程环境，首版不允许 Gateway 直接终止或重启自身。
63. Rule 51 的同步 L0 sink 边界继续有效：事务内只写 L0 和幂等账本，不调用模型、网络或异步实现。新增提炼调度只能发生在该事务成功提交之后，通过显式注入的小接口把已提交 session 通知给上游 pipeline；通知不得进入 Hook 一秒响应预算，不得使已成功的 L0 捕获回滚或改报失败。模型未配置、未授权、重启未应用、调度或提炼失败时必须保留 L0，且不得推进 L1 cursor 或把失败批次标记为已完成；不得阻断 Agent 或无限重试，后续增加调度状态或重试时必须有界、脱敏且不能改变上述事务边界。
64. Hook L0→L1 的产品闭环必须沿用上游已验证的会话调度语义：新会话 warm-up、后续轮次阈值和 idle timer 均由 pipeline 权威处理，产品 Adapter 不复制阈值算法。新 L1 必须保留真实 L0 来源并默认进入 `pending` 收件箱；只有 `approved`、有效且未被治理抑制的 L1 才能在下一轮通过预算召回。自动本地捕获、模型外联/提炼和自动召回是三项独立能力，任何一项授权不得隐式批准其他两项。
65. 模型外联撤销与密钥删除必须是两个独立、可理解的操作。撤销只追加版本化撤销记录，并在受管重启后停止新的模型请求和 L1–L3 提炼；不得删除 `gateway.env` 中的 API Key、模型配置或任何记忆。删除模型配置必须单独确认，从 `gateway.env` 移除模型字段和 API Key，但仍不得删除记忆。Web 与用户文档必须披露密钥的 macOS/Linux 本地路径、授权用途、可能发送的数据、服务商费用/数据规则、重启要求及两种操作的效果。
66. 模型提炼请求和响应是内部管线任务，禁止进入 L0。提炼 runner 必须直接调用模型接口而不经过 Agent 生命周期 Hook，模型输出只允许进入 L1–L3 处理；所有兼容上游 session 的捕获入口必须排除内部 memory pipeline session，防止递归提炼和 L0 无界增长。
67. 文档事实源按职责分层：`README.md` 是当前版本唯一完整用户手册，只描述用户真实可用能力和明确限制；`docs/TECHNICAL_DESIGN.md` 是当前总体技术方案并链接细分契约；`docs/architecture/*.md` 冻结具体接口与安全不变量；本文件冻结不可违反的产品和工程决策；`docs/implementation-records/` 只保存历史实施证据；根目录 `README_CN.md` 是 TencentDB-Agent-Memory 上游参考，不是 PersonalMemory 使用说明。`CURRENT_ARCHITECTURE.md` 不得与总体技术方案形成双重当前事实源，应收口为上游基线和历史差异入口。
68. 正式安装必须提供用户级 `personalmemory` 命令入口，默认受管安装到 `~/.local/bin/personalmemory`，但不得擅自修改 `.zshrc`、`.bashrc` 或其他 shell 配置；目录不在 `PATH` 时只输出明确提示。命令至少统一提供 `status`、`open`、`restart`、`stop`、`backup` 和显式 `token show`，并通过当前安装源码复用既有生命周期实现，不复制数据删除或进程管理逻辑。`token show` 只允许交互式终端显式调用，读取前验证私有普通文件和严格令牌格式，不进入状态 JSON、日志或命令回执。安装、重复安装、升级和卸载必须以独立私有回执和内容摘要精确管理该入口；同路径未知文件、用户修改或路径扩张必须 fail closed。

## 6. 工程与质量

1. `main` 始终保持可运行；功能分支短生命周期、小步合并。
2. 引入上游代码必须保留原始 LICENSE、版权和第三方归属说明，不暗示腾讯官方背书。
3. 数据库 schema 必须版本化；升级必须提供迁移路径，高风险迁移应支持回滚或备份恢复。
4. 关键闭环必须有自动化验收：捕获、提炼、召回、纠错、导出、恢复和彻底删除。
5. 性能数字必须经过目标设备实测，不把上游数据或设计目标直接当作 PersonalMemory 的能力承诺。
6. 日志默认不记录记忆正文、密钥或其他敏感内容；必要诊断信息应脱敏。
7. 索引应能够从可导出的事实资产重建，避免不可读数据库成为用户数据的唯一载体。
8. 开发严格按 [实施计划](IMPLEMENTATION_PLAN.md) 的步骤推进；每个步骤都必须经过实施前检查、验证检查和代码审查，全部通过后才能提交并进入下一步。
9. 代码审查发现阻断问题时不得带病进入后续步骤；修复后必须重新执行受影响的检查。
10. 每个步骤的检查和审查结论应留在提交信息、开发记录或可追溯的审查记录中，不能只口头宣布通过。
11. 腾讯上游同步必须遵循 [上游同步 Runbook](UPSTREAM_SYNC_RUNBOOK.md)：先固定 SHA 和 merge-base、逐提交分类并隔离验证；不得假定 `main`、`feat/server` 与 `feat/server_team` 可以直接互相合并。

### 6.1 Git 提交规则

1. 后续开发过程中，完成一个边界清晰、可独立验证的变更单元后，应主动执行 Git commit，无需每次等待用户提醒。
2. 提交前必须检查变更范围、敏感信息、格式及与本次任务相关的测试；不得把无关修改混入同一提交。
3. 提交应保持原子性：一个提交只表达一个主要意图，文档和实现可在同一功能提交中同步更新。
4. 提交标题采用 `<type>: <description>` 格式；描述简洁说明结果，默认使用中文，不以句号结尾。
5. 允许的 `type` 及用途：
   - `feat`：新增功能；
   - `fix`：修复缺陷；
   - `perf`：提高代码性能；
   - `style`：只修改代码格式，不改变行为；
   - `refactor`：既非功能新增也非缺陷修复的代码重构；
   - `test`：新增或更新测试；
   - `ci`：持续集成、部署配置或相关服务单元变更；
   - `docs`：用户文档或开发文档更新；
   - `chore`：构建流程、依赖管理或辅助工具等其他变更。
6. 不得在 commit 标题、正文、作者、共同作者或其他元数据中添加 `Codex`、`Claude`、`AI generated` 等 AI 生成标记。
7. 不擅自改写已共享的 Git 历史；除非用户明确要求，不执行 rebase、amend、force push 等会改变既有提交的操作。
8. 是否推送远端与本地 commit 分开处理；除非用户明确授权，不自动执行 Git push。

### 6.2 安装与首次使用

1. 完整产品必须以“一条命令完成安装并进入可用状态”为目标，不要求普通用户手工安装多个运行时、编辑多份配置或理解内部服务拓扑。
2. 安装命令应完成环境检查、组件获取、配置初始化、服务启动和健康检查，并给出明确的成功结果及下一步入口。
3. 必填密钥或模型配置无法自动获得时，安装流程应提供交互式引导或清晰的单一配置入口，不能以隐式默认值外发用户数据。
4. 安装过程应幂等、可诊断；重复执行不得破坏已有数据，失败时应说明原因和恢复方法。
5. 同时提供升级、备份恢复和卸载能力；卸载程序不得在未明确确认的情况下删除用户记忆数据。
6. 发布验收必须覆盖干净环境的一条命令安装测试，并记录支持的平台、架构、耗时和已知限制。
